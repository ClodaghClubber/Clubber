Fixtures API for Clubber

The Fixtures Dashboard as an API: every fixture it collects from county, provincial, college and rugby websites, its status, edits, crew and history, plus the Clubber game ready to create. It reads and writes the same data as the dashboard, so both can be used during the switch-over.

Base URLhttps://gaa-fixtures-proxy-v2.clodagh-b01.workers.dev/api/v1
AuthAuthorization: Bearer <key>
FormatJSON, UTF-8
Specdocs/clubber-api.openapi.yaml

Getting started

  1. Get the API key from Clodagh. Send it on every request as Authorization: Bearer <key> (or X-API-Key: <key>). Keep it server-side: it can approve and edit fixtures.
  2. Check the API is up: GET /health needs no key and returns configured: true once the key is set.
  3. Load the fixtures for a date range with GET /fixtures, then poll GET /changes to stay up to date.
curl -H "Authorization: Bearer $FIXTURES_API_KEY" \
  "https://gaa-fixtures-proxy-v2.clodagh-b01.workers.dev/api/v1/fixtures?from=2026-11-20&to=2026-12-20&status=Approved&site=IE"

Send the name of the person using Clubber with every change, as "user": "Aoife" in the body or an X-User-Name header. The dashboard's history then shows Aoife (Clubber). Without a name it shows Clubber.

Dates and times

  • All dates are YYYY-MM-DD. Fixture date and time are Irish local time (24-hour HH:MM); time is null when there's no throw-in time yet.
  • The Clubber game in clubber.game uses UTC, exactly as Clubber's GameDetails import expects. 00:01 there means no time yet.
  • Timestamps (updatedAt, history at) are ISO 8601 UTC.

The fixture

FieldMeaning
countyA county, or a grouping: Munster, Leinster, Munster PPS, Leinster PPS (schools), Higher Education, BUCS, ACE, Champ.
teamA / teamBNames as the source website writes them. The Clubber club names and IDs are in clubber.game.

missing.teamsThe teams aren't decided yet ("Winner SF1"). The game can't be created until they are.

clubber.gameThe game exactly as the dashboard's Clubber export would create it: club IDs, grade, championship type, round, price, UTC date and time, and a venue only when it exactly matches a Clubber venue.
clubber.liveThe game as Clubber has it now, when gameId is in Clubber's upcoming-games feed. differences lists date or time mismatches.
updatedAtWhen anything about the fixture last changed.

List fixtures

GET/fixtures

Fixtures dated from from to to, both inclusive. If you leave them out, you get today to 30 days ahead (Irish time). One request can cover at most 366 days. Results are sorted by date, time and county, 500 per page by default.

One fixture

GET/fixtures/{id}

Returns { "ok": true, "fixture": { … } }, or 404 if the fixture has gone (removed, or no longer on the source website).

Approve, reject and edit

PATCH/fixtures/{id}

Send only what changes. Each change is saved exactly as the dashboard saves it and shows in the fixture's history.

FieldValues
statusProposed, Approved or Rejected
date, time2026-11-28, 19:30 (Irish time; null = no time)

PATCH /fixtures/f_Q29ya3x…
{ "user": "Aoife", "status": "Approved" }

PATCH /fixtures/f_Q29ya3x…
{ "user": "Aoife", "time": "20:15", "venue": "Páirc Uí Rinn" }

→ { "ok": true, "changed": ["time", "venue"], "fixture": { … } }

After an edit, clubber.game is worked out again, so a new time is converted to UTC and a new venue matched against Clubber's venues.

Edits stick. Once a field is edited it keeps your value, even if the source website changes it later. If the source changes the date, teams or competition, the fixture can come back as a new id with status Proposed; the old one disappears from the list and shows as removed in changes.

Many at once

POST/fixtures/batch

Up to 500 updates in one request, for example approving a selection. Every update takes the same fields as PATCH. If any id is unknown or any field is invalid, nothing is saved.

{ "user": "Aoife",
  "updates": [ { "id": "f_Q29ya3x…", "status": "Approved" },
               { "id": "m_mabc123",  "status": "Rejected" } ] }

→ { "ok": true, "results": [ { "id": "f_…", "changed": ["status"], "fixture": { … } }, … ] }

Add a fixture

POST/fixtures

Adds a fixture by hand, as the dashboard's Add fixture does. It starts as Proposed unless you send status. county, teamA, teamB and date are required, and code is worked out from the competition when you leave it out. The same fixture twice (same county, teams, competition and date) returns 409 with the existing id.

{ "user": "Aoife", "county": "Cork", "teamA": "Sarsfields", "teamB": "Midleton",
  "date": "2026-12-06", "time": "14:00", "competition": "Premier Senior HC",
  "round": "Final", "venue": "Páirc Uí Chaoimh", "status": "Approved" }

→ 201 { "ok": true, "fixture": { "id": "m_mmwp4lvu1vhs3", "kind": "manual", … } }

Remove

DELETE/fixtures/{id}

The dashboard's Remove. It only works on Rejected fixtures; reject the fixture first, or you get 409. Fixtures added by hand are deleted. Scraped fixtures are marked Removed and won't come back from the source website.

Creating the game in Clubber

  1. List the Approved fixtures that aren't in Clubber yet: GET /fixtures?status=Approved&inClubber=false.
  2. For each one where clubber.ready is true, create the game from clubber.game. Show clubber.warnings to the person approving.
  3. Record the new game: PATCH /fixtures/{id} with { "clubberGameId": "…", "clubberCreated": true }. The dashboard then shows it as In Clubber, and clubber.live / differences start tracking it.
  4. When a fixture already in Clubber changes (see Keeping in sync), compare clubber.game with your game and update it. clubber.differences flags date and time mismatches.

Fixtures with errors (club not found, team not confirmed, no grade) need fixing first, usually by mapping the club on the dashboard. Show the errors to the person approving rather than creating a partial game.

Keeping in sync

GET/changes?since=…

Every fixture whose content changed after since, oldest first. Anything counts: a source website changing the date, time or venue; a status change or edit made on the dashboard or through the API; a Clubber or crew change; a new fixture; or one that's gone. Add from / to to limit it to fixtures dated in a range.

GET /changes?since=2026-11-20T15:00:00Z

{ "ok": true, "since": "2026-11-20T15:00:00.000Z", "asOf": "2026-11-20T16:00:02.114Z",
  "trackingSince": "2026-11-20T15:20:06.366Z", "complete": true, "total": 2,
  "changes": [
    { "id": "f_…", "change": "changed", "at": "2026-11-20T15:48:10.002Z", "fixture": { … } },
    { "id": "f_…", "change": "removed", "at": "2026-11-20T15:48:10.002Z", "fixture": null } ] }
  1. Do a full load with GET /fixtures and keep the time you made it.
  2. Every few minutes, call GET /changes?since= with the previous response's asOf.
  3. Upsert each changed fixture and drop each removed one.
  4. If complete is false, your since is from before change tracking started, so do a full load again.

Source websites are checked hourly, so polling every 5–15 minutes is plenty.

Webhook (optional)

If Clubber gives us a URL, the dashboard will POST to it once an hour whenever something has changed. The post lists only ids; fetch the details with GET /fixtures/{id} or /changes.

POST https://your-clubber-endpoint
X-Fixtures-Signature: sha256=<hex HMAC-SHA256 of the raw body, keyed with the shared secret>

{ "event": "fixtures.changed", "since": "…", "asOf": "…", "count": 2, "truncated": false,
  "changes": [ { "id": "f_…", "change": "changed", "at": "…" },
               { "id": "f_…", "change": "removed", "at": "…" } ] }

Reply with any 2xx status. If the post fails, the same changes are sent again the next hour. Verify the signature by computing the HMAC of the raw body yourself and comparing it with the header.

History

GET/fixtures/{id}/history
GET/history?from=…&to=…

Status changes, edits, In Clubber and Clubber Pick changes, oldest first, with who made them and on what device. For /history, from / to are the days the changes were made (Irish time); add type=status or type=edit to narrow it. The shared store keeps the latest 500 status changes and 2,000 edits.

{ "type": "status", "at": "2026-11-19T21:46:16.887Z", "user": "James", "device": "Windows",
  "changes": [ { "field": "Status", "from": "Proposed", "to": "Approved" } ], "note": "" }

Read fixtures from a screenshot

POST/import

The dashboard's Add from screenshot. Send up to 10 images or PDFs (base64) and/or pasted text. Claude reads the fixtures, and each comes back with up to 3 existing fixtures it may match (same teams, within six weeks). Nothing is saved: add new ones with POST /fixtures, or update a match with PATCH. It can take up to a minute.

{ "files": [ { "name": "cork.png", "mediaType": "image/png", "data": "iVBORw0KGgo…" } ],
  "texts": [ { "name": "email", "text": "Sat 28 Nov, Donoughmore v Killeagh, 7.30pm, PUC" } ],
  "note": "Cork hurling" }

Errors and limits

Errors return a 4xx or 5xx status with a code you can act on:

{ "ok": false, "error": { "code": "range_too_long", "message": "A request can cover at most 366 days" } }
StatusWhen
400Bad parameter or field: invalid_range, range_too_long, invalid_status, invalid_time, unknown_fields…
401Missing or wrong API key
404No such fixture (or endpoint)
409Not allowed now: removing a fixture that isn't Rejected, or adding one that already exists
502Reading a screenshot failed
503The API key hasn't been set up on the server yet
  • Date range: up to 366 days per request. Page size: up to 2,000. Batch: up to 500 updates.
  • Writes go to the same store as the dashboard, last write wins. Avoid two people changing the same fixture at the same moment.
  • The Clubber fields come from the dashboard's own export rules, so the API and the dashboard always agree on club IDs, grade, price and time.
